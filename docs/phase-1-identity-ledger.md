## 2 各任务完成条件

### F1-01 工作区与运行环境

- 创建 apps/web、apps/api、packages/contracts、packages/database；Fastify 的 app 工厂与监听入口分开。
- 提供 dev、build、typecheck、lint、test、test:integration、test:e2e、db:migrate 命令，并能从仓库根目录执行。
- 开发和测试使用不同数据库；记录连接方式。当前 PATH 未找到 docker/psql，实施时先核实可用实例，必要时准备本地容器环境，不静默改装全局软件。
- 环境变量示例包含 DATABASE_URL、TEST_DATABASE_URL、PUBLIC_ORIGIN、GitHub App 登录配置及首个管理员 GitHub 数字 ID，不写真实秘密。
- 出口：干净安装可构建；前后端启动；数据库连通。此时页面可以是最小壳，不开始搭建小镇。

### F1-02 接口契约与基础迁移

- 按数据库设计创建 13 张表及索引，schema 来源集中在 database 包；账本函数在 F1-05 加入。
- 定义十进制整数字符串金额、分页游标、统一身份上下文和错误码；契约不导出数据库的私有字段。
- 建立 member/admin 固定角色及 Agent 权限开关；系统账户初始余额为 0，发行预算缺省为 0。
- 出口：空 PostgreSQL 18 可按顺序迁移；重复运行迁移不会重复初始化账户；用户 GitHub ID、账户唯一性和非负额度约束生效。

### F1-03 GitHub 登录与内测准入

- 使用一个 GitHub App，阶段 1 只取用户身份；不要求先安装仓库，不申请写仓库能力。
- state 一次性、10 分钟过期且与浏览器绑定；PKCE 使用 S256。OAuth 网络请求在短事务之外执行，重入回调不能产生重复用户。
- 站内 Session 保存摘要并设置安全 Cookie；退出撤销 Session；写请求校验 CSRF，错误 state 或不可信回调不得创建 Session。
- 新用户为 pending，管理员批准后为 active；首次管理员只由明确配置的 GitHub 数字 ID 建立。
- 出口：真实用户能完成登录；伪造、过期和重放回调失败；pending 用户不能创建 Agent。

### F1-04 Agent 与访问凭证

- 同一事务创建 Agent、默认策略和 AVAILABLE/RESERVED 两个零余额账户。此前需合入 F1-05 的开户函数后完成此项集成。
- owner 才能修改名称、暂停状态、策略和 key；Agent key 只能代表绑定 Agent，不可指定其他 owner 或 Agent。
- secret 仅首次返回；列表仅显示 key ID、标签、有效期和撤销状态。丢失 secret 时支持撤销并重新创建。
- 构造 user、agent、system 三类 actor；外部请求不能伪造 system。暂停、凭证撤销与用户停用语义按架构执行。
- 出口：两个用户相互替换路径 ID 仍无法越权；Agent 不可自行提高限额、创建 key 或变更 owner。

### F1-05 唯一记账入口

- 实现受限 post_journal 和零余额开户函数；交易头、完整分录与余额一次提交，函数参与调用者现有事务。
- 借贷不平衡、非法账户组合、非正金额和结果为负的余额全部拒绝；ISSUANCE_CONTROL 只允许发行命令使用。
- 同业务键同内容返回原结果并标记 created=false，不同内容返回冲突；不允许在已完成交易上追加分录。业务回放不得再次更新发行预算、hold 或合同状态。
- 运行角色无权直接改余额、写交易头/分录或修改函数；迁移角色与运行角色使用不同凭证。
- 出口：运行角色的绕过写入被数据库拒绝；外层事务主动失败时，账户、流水及开户结果全部回滚。

### F1-06 发行与冻结基础能力

- issue 在锁定月预算后给平台奖励池发行；发行预算检查和流水同事务完成。
- reserve 冻结、adjustHold 调整未最终处理的冻结，finalizeHold 一次完成全部支付及退款，pay 处理领域命令中的即时消费。
- 内部命令必须包含服务端生成的 business_key、actor、业务原因；不信任客户端提交的任意 source/target 账户。
- 同一个 hold 的最终支付与取消只允许一个终态；分账及退款总额必须等于剩余冻结。
- 出口：100 积分可冻结、分成 70 和 30，或支付 70 并退回 30；全部账户和发行控制账户能够对账。演示通过测试夹具完成，不增加生产测试打钱接口。

### F1-07 授权预算与交易幂等整合

- 新承诺校验当前用户、Agent、key、功能权限、单笔及每日预算；owner 代操作适用同一预算规则。
- 预算采用当日已结算 spend_points 加全部未结清 hold；改变 hold 和支出的所有路径共用策略行锁。
- 原合同最终结算不重新要求新增消费权限；暂停、降额或撤销旧 key 不阻断合法的系统履约。
- 幂等回执与业务同事务提交；同请求键不同参数报冲突，换请求键重复同业务仍不再次支付。
- 出口：并发两笔各 80 的冻结在余额或日限额 100 时只成功一笔；跨日、降额、失败回滚和响应丢失后重试行为符合规格。

### F1-08 审计与运营接口

- 管理员能够批准内测用户、设置发行月预算、执行有理由的发行并查询结果；不提供任意账户加余额。
- 凭证撤销、暂停、策略调整、预算调整、发行和账本业务均可查实际操作者、业务编号及时间。
- 对账核验账户缓存与分录、冻结余额与 hold、累计发行与系统账户关系；输出差异，不自动修改历史。
- 运营只读查询支持账户、Agent、用户和业务键过滤并分页；禁止返回 secret、Cookie 或 OAuth token。
- 出口：每笔管理操作都有可追溯记录，普通用户和 Agent 无法调用管理写接口。

### F1-09 管理台与钱包界面

- 提供登录、待准入、我的 Agent、创建 Agent、策略与暂停、凭证管理、钱包和流水、最小运营页面。
- 金额使用十进制字符串展示与输入校验；余额分别显示可用和冻结。失败信息说明原因，网络不确定时按业务编号查询。
- 凭证首次显示需清楚提示保存，并支持撤销；刷新或回查不再显示 secret。
- 权限表单使用版本号避免静默覆盖并发修改；消费开关默认关闭，额度为零。
- 出口：用户可独立管理自己的 Agent；页面按钮与服务端权限一致；钱包未收入时明确显示零余额，不能伪造工作成果演示到账。

### F1-10 PostgreSQL 集成验收

- 执行下节 T01 至 T12，必须使用真实 PostgreSQL 18 和应用实际运行角色。
- 并发测试使用独立连接和同步起点，验证最终余额、流水数、冻结状态及事务回滚，而不只检查 HTTP 状态码。
- 首次出现失败先定位规则或实现原因；不得通过放宽断言、跳过并发或改用内存数据库宣称通过。
- 出口：所有关键场景通过，失败记录可以定位到业务编号，运行日志没有凭证明文。

### F1-11 浏览器验收与真实登录验证

- Playwright 覆盖准入后的用户创建 Agent、修改策略、发放及撤销 key、查看钱包和退出。
- 自动化测试可模拟 GitHub 网络响应；上线前另完成一次真实 GitHub App 登录，确认回调和 Cookie 配置。
- 验证两个账号的资源隔离、CSRF 拒绝、失效 Session 与已撤销 key 的行为。
- 出口：浏览器流程与后端记录一致；明确区分模拟 OAuth 测试与真实登录验证结果。

## 3 对外 API 清单

下列为阶段 1 的接口边界，路径最终由 contracts 包固定。浏览器写请求需要 Session 和 CSRF；Agent 使用 Bearer key。读取钱包前均校验 owner 或绑定 Agent。

| 接口 | 调用方 | 作用 |
| --- | --- | --- |
| GET /api/v1/auth/github/start | 浏览器 | 创建 state/PKCE 并跳转授权 |
| GET /api/v1/auth/github/callback | 浏览器回调 | 校验授权并建立站内 Session |
| GET /api/v1/me | 用户或 Agent | 返回当前主体、状态及有效权限，不返回 secret |
| POST /api/v1/auth/logout | 用户 | 撤销当前 Session |
| GET、POST /api/v1/agents | active 用户 | 查看所属 Agent、创建 Agent |
| GET、PATCH /api/v1/agents/:id | owner；GET 可供绑定 Agent | 查看详情，owner 修改名称或暂停状态 |
| GET、PUT /api/v1/agents/:id/policy | owner；GET 可供绑定 Agent | 查询或按 version 更新授权和限额 |
| GET、POST /api/v1/agents/:id/keys | owner | 查询元数据、创建一次性显示的凭证 |
| POST /api/v1/agents/:id/keys/:keyId/revoke | owner | 撤销凭证，重复撤销保持成功 |
| GET /api/v1/agents/:id/wallet | owner 或绑定 Agent | 查看可用、冻结余额及预算占用 |
| GET /api/v1/agents/:id/transactions | owner 或绑定 Agent | 游标分页查询其可见流水 |
| GET /api/v1/operations/:id | 有权访问该资源的主体 | 查询自己的业务结果，避免超时后盲目重提 |
| GET /api/v1/admin/users | admin | 按准入状态分页列出用户 |
| GET、PATCH /api/v1/admin/users/:id | admin | 查看、激活或暂停用户 |
| GET、PUT /api/v1/admin/issuance-periods/:month | admin | 查询或设置月发行上限 |
| POST /api/v1/admin/issuances | admin | 按预算发行到平台奖励池，必须带原因和幂等键 |
| GET /api/v1/admin/ledger、/api/v1/admin/audit-events | admin | 查询账本与审计 |

GET /operations/:id 对应已保存的业务回执及其资源授权；没有回执的请求不能凭不存在的 ID 推断资金失败。响应丢失时也可以重发相同幂等键，由原命令返回同一结果。

不开放 /transfer、任意余额 PATCH、公开 hold 创建或直接结算接口。issue、reserve、adjustHold、finalizeHold、pay 是内部服务方法，由受权的运营或后续业务入口调用。

错误至少区分 UNAUTHENTICATED、ACCESS_DENIED、ACCOUNT_PENDING、AGENT_PAUSED、CREDENTIAL_REVOKED、POLICY_VERSION_CONFLICT、INSUFFICIENT_FUNDS、SPEND_LIMIT_EXCEEDED、ISSUANCE_LIMIT_EXCEEDED、IDEMPOTENCY_CONFLICT、BUSINESS_ALREADY_FINALIZED。跨 owner 访问不泄露对方私有数据是否存在。

## 4 第一阶段关键测试

| 编号 | 场景 | 必须结果 |
| --- | --- | --- |
| T01 | 伪造、过期、重放 OAuth state；同一 GitHub ID 重复登录 | 不创建非法 Session，不创建重复用户 |
| T02 | 两个用户替换 Agent、policy、key 和 wallet 路径 ID | 不能读取或修改对方私有资源 |
| T03 | key 撤销、用户或 Agent 暂停与新写入并发 | 撤销完成后新请求拒绝；既有合法履约继续，历史不撤回 |
| T04 | 凭证创建响应丢失并以同一请求键重试 | 只有一个 key，无 secret 回放；可撤销后重新创建 |
| T05 | 月发行上限 100，同时两次发行 80；随后更换请求键重放成功业务 | 仅一笔成功；重放不再次增加 issued_points，发行累计与奖励池及控制账户一致 |
| T06 | 可用余额 100，同时冻结两笔 80 | 一笔成功，可用 20、冻结 80，无负余额 |
| T07 | 同一冻结同时结算和取消，或换请求键重复结算 | 只有一个最终结果，不出现重复付款或退款 |
| T08 | 冻结 100，支付 70、退款 30；外层业务主动抛错 | 正常时金额守恒；抛错时余额、hold、流水和回执均回滚 |
| T09 | 昨日冻结 80、今日消费 10，上限 100；随后支付 60 并退回 20 | 新承诺最多 10；结算后预算占用 70，不重复计数 |
| T10 | owner 代操作、拆分增加同一冻结、降额后履约 | 新承诺同样受权限与预算限制；单笔限制不能拆分绕过；旧合同可结算 |
| T11 | 不平衡分录、非法账户类型、直接改账或追加旧分录 | 记账函数或数据库权限拒绝；合法历史保持不变 |
| T12 | 9007199254740993 积分的合法测试数据在数据库、API、界面往返 | 数字完全一致；对账能够核验全部账户，不使用 number 计算 |

T12 仅用于隔离测试环境验证 bigint 精度，不代表实际发行预算。测试之间重置独立测试数据，不清空开发或运营数据库。

## 5 阶段完成定义与后续衔接

完成阶段 1 需要同时满足：可运行且可复现的工作区；真实登录和内测准入；正确的 Agent 归属与凭证撤销；唯一记账入口及审计；T01 至 T12 全部通过；管理台关键流程通过；没有公开自由转账或测试加余额入口。

GitHub App 注册参数和可用 PostgreSQL 开发实例是实施所需外部条件。未提供时可以完成结构、mock 登录测试和数据库规格，但真实登录及数据库集成验收必须保持未完成，不能以文档或模拟结果替代。

阶段 2 从任务发布时调用 reserve、验收或取消时调用 finalizeHold 开始；不需要重做钱包。阶段 4 的 API 费用账本、阶段 5 的产权表和阶段 6 的地图按对应模块接入。API 供应商、月度奖池数额和土地价格不是阶段 1 的前置依赖。
